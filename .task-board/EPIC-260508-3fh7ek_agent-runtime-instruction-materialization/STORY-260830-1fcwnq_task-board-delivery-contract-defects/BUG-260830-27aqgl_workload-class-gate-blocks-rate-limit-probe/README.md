# BUG-260830-27aqgl: workload-class-gate-blocks-rate-limit-probe

## Description
When spawn.workload_classes is configured, a provider limit group in state probe_eligible can never be probed, so rate-limit recovery deadlocks permanently. The spawn plane's designed recovery is a claim gate: exactly one next spawn probes the group, and that launch exiting 0 clears it to available. But the workload-class recommendation drops any pair whose group is not already available, reporting reason provider_limit_group_unavailable, so available_pairs is empty and every spawn is refused with workload_class_pair_unavailable_in_snapshot. The only mechanism that could perform the probe is blocked by a gate that treats probe_eligible as unavailable. Observed 2026-08-30: task-board limits show reported 'codex-plan probe_eligible (stored suppressed), next probe 2026-08-30T12:34:36Z' with the probe time already two hours past; 'task-board limits clear --group codex-plan' succeeded and re-armed the gate at step 0 with next probe now; preflight still reported available_pairs 0 and dropped provider_limit_group_unavailable; a spawn then refused with workload_class_pair_unavailable_in_snapshot. The suppression's recorded evidence was RUN-260830-3180e9 gpt-5.6-sol 'you have hit your usage limit', and an ARMED FAULT INJECTOR was simultaneously configured to emit simulated usage_limit output, so the suppression may have originated from a simulated fault rather than a real quota exhaustion. Effect: roughly ninety minutes of a working session were spent waiting on a recovery that could not occur.

## Acceptance Criteria
A provider limit group in probe_eligible state is offered to exactly one spawn so the claim-gated probe can run, whether or not spawn.workload_classes is configured. The workload-class recommendation distinguishes 'suppressed and not yet probe-eligible' from 'probe_eligible' and does not filter the latter as unavailable, or it explicitly hands the probe through a documented path. A configuration that would make the probe unreachable is refused at config-parse time rather than deadlocking at spawn time. The refusal message, when a pair really is unavailable, names the group state and the next probe time so an operator can tell waiting from deadlock.
