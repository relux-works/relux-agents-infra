### 0552 — MLX Swift Cannot Serve This Model's Context, And The Failure Traps Rather Than Throws
- DECISION: **REJECT the MLX Swift migration.** Python `mlx-lm` stays the default local Qwen runtime. `benchmark-compare` exit 3, four blockers, two hard. Measured sequentially on one host (M1 Max / 64 GiB / build 25F80) against the real 28 GB `Qwen3.8-27B-Uncensored-MLX-8bit`: Python `mlx-lm` 0.32.0 @ `9150698` with `mlx` 0.32.2, Swift `mlx-swift` 0.31.6 / `mlx-swift-lm` 3.31.4.
- REGRESSION: the 75k-context run **aborts the Swift process**. `Fatal error: [metal::malloc] Attempting to allocate 255904140288 bytes which is greater than the maximum allowed buffer size of 41747087360 bytes`, SIGTRAP. The Python baseline served the same 73,054-token prompt in 822 s.
- ROOT CAUSE, verified to the byte: 255,904,140,288 ÷ (24 heads × 2 bytes) = 73,016² exactly — one full `[1, 24, n, n]` fp16 attention array over the whole prompt. `MLXVLM.Qwen35VLModel.prepare(_:cache:windowSize:)` declares its window parameter as `windowSize _: Int?` and **discards it**, pushing the entire prompt through the language model in one call. `GenerateParameters.prefillStepSize` (default 512) is therefore inert for this model, and no prototype flag can chunk that prefill. `mlx_lm` chunks its own, which is why the same prompt succeeds there.
- FINDING, and the one with the widest blast radius: MLX's default error handler calls `fatalError`, so an allocator failure is a **trap, not a throw**. None of the machinery TASK-260827-2h39ya and TASK-260827-2q77g8 built ran — no `generation_worker_failed`, no `/health` 503, no `generation_worker_unavailable` marker, no deferred teardown, no supervised restart. All of it was built for a thrown error. mlx-swift 0.31.6 *does* expose `withErrorHandler` / `withError` to convert MLX errors into Swift throws and the prototype does not use them; adopting them would buy a clean condemnation and a supervised replacement, not a served request.
- MEASUREMENT: capacity bounds. 15,589 tokens succeeds at **56.31 GiB — 88 % of the host**; ~73k aborts. Metal's single-buffer limit alone caps n at 29,491; the host binds first, around 17–18k by a two-point extrapolation (labelled as such in the report).
- MEASUREMENT: prefill is the other hard blocker. 8k prompt — Swift 75.5 tok/s vs Python 109.4 (**0.69x**, threshold 0.90), TTFT 103.0 s vs 71.5 s (**1.44x**, threshold 1.10). Decode is a genuine Swift win (1.03x short, 1.02x at 8k) and so is short-prompt TTFT (0.75x), but none of it survives the abort. Peak footprint 1.094x — inside the 1.10 band with a 6 % margin, and 44.01 GiB vs 31.47 GiB at an 8k prompt.
- MEASUREMENT: the teardown-abandonment risk, finally sized on the real model instead of the 261 MB fixture. Provoked with the real fault seam: outcome **abandoned** after **9.988 s**, with **29,744,368,205 B — 27.70 GiB, 43 % of the host — left in MLX's pool** until the supervisor replaces the process. The weights genuinely came back (0 of 1229 live `Module` owners, container deallocated, `returned_bytes` 29,684,985,407 clearing the 29,501,612,496 footprint); the refusal is on **7,984 bytes** of post-generation sampler/RNG state against a zero allowance. Frequency under benchmark load: **0 of 27 generations** — and the one real failure that did occur bypassed the path entirely by trapping.
- FINDING: **the incumbent's prompt cache buys nothing on this model**, which removes the prototype's headline gap. Deployed with `--prompt-cache-size 1 --prompt-cache-bytes 8GB`, the 3-turn shared-prefix scenario re-prefilled in full every turn (0/7822, 0/7851, 0/7880) with the cache populated at 1 sequence / 0.67 GB.
